# Changeset 작성

이번 변경의 릴리스 대상·증가 종류·변경 설명을 `.changeset/*.md`에 기록해요.
판단 기준과 예시는 저장소 루트의 `docs/release-workflow.md`를 원본으로 사용해요.

## 변경 범위

- `AGENTS.md`, 릴리스 문서, `git status --short`, 현재 브랜치·HEAD SHA를 확인해요.
  비교 기준은 사용자 지정, 확인 가능한 PR 대상, `develop` 순서예요. 실제 사용할 ref를 기록하고
  fetch하지 않았다면 최신 원격이라고 단정하지 않아요.
- 공통 조상부터의 실제 diff와 필요한 호출부를 읽어요. 현재 브랜치는 미커밋·미추적 변경도
  기본 포함하되 사전 작업과 생성 파일을 구분해요. `커밋된 변경만` 요청이면 HEAD까지만 봐요.
- 기존 changeset을 먼저 읽어요. 기준 브랜치에서 물려받은 파일은 수정하지 않고, 이번 브랜치의
  동일 변경을 담는 파일이 있다면 중복 생성 대신 갱신해요. 관련 없는 사전 파일은 보존해요.

## 작성과 확인

- 파일 경로만으로 판단하지 않고 실제 공개 API·사용자 동작·소비 패키지 영향을 확인해요.
  직접 릴리스할 패키지를 선택하고, 의존 패키지의 자동 버전 증가는 CLI 결과로 확인해요.
- 변경 근거에 따라 patch/minor/major를 선택해요. 호환성·운영 정책이 불명확하면 필요한 정보를
  확인하고, 근거 없는 버전이나 미확정 정책을 기록하지 않아요.
- 릴리스가 필요 없으면 파일을 만들지 않고 PR에 넣을 구체적인 생략 사유를 제공해요.
- 필요하면 고유한 이름의 Markdown 파일을 직접 작성해요. frontmatter에는 실제 workspace
  패키지 이름과 증가 종류를, 본문에는 무엇이 바뀌었는지와 필요한 사용처 변경 방법을 적어요.
  `package.json` 버전과 CHANGELOG 갱신은 버전 PR에 맡겨요.
- 요청한 범위의 설명과 파일을 확인하고 `pnpm changeset:check`,
  `pnpm changeset status --verbose`를 실행해요. 커밋된 변경만 요청했는데 작업 트리가 다르면
  해당 SHA의 별도 환경에서 확인하거나 CLI 결과가 현재 작업 트리 기준임을 밝혀요.
  CLI가 없거나 실패하면 실행 불가 사유를 구분하고 성공했다고 쓰지 않아요.

대상 SHA·미커밋 포함 여부, 패키지·증가 종류·근거, 생성·수정 파일 또는 생략 사유,
실제 검증 결과를 짧게 전달해요. 스킬 호출만으로 커밋·push·PR 게시·병합은 하지 않아요.
