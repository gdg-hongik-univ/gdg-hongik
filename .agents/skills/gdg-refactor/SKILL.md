# 브랜치 범위 리팩토링

이번 변경을 이해하고 유지하는 데 도움이 되는 정리만 수행해요. 개선할 지점이 없으면
수정 없이 그 이유를 알려요. 경로는 저장소 루트 기준이에요.

## 범위 확인

- 루트와 대상 경로의 `AGENTS.md`, 관련 README를 읽고 `git status --short`, 현재 브랜치를 확인해요.
  기존 작업을 보존하고 리팩토링 요청만으로 커밋·push를 하지 않아요.
- 비교 기준은 사용자 지정, 확인 가능한 PR 대상, `develop` 순으로 정해요.
  실제 사용할 ref를 확인하고 fetch하지 않은 원격 추적 ref를 최신이라고 단정하지 않아요.
- `git merge-base HEAD <comparison-ref>`의 공통 조상부터 `git diff <merge-base-sha>`를 읽고,
  `git ls-files --others --exclude-standard`로 미추적 파일도 확인해요.
  사용자가 커밋된 변경만 지정하면 `git diff <merge-base-sha> HEAD`로 범위를 정해요.
- 전체 변경과 필요한 호출부를 먼저 확인해요. 정리 대상은 이번 변경과 직접 관련된 코드로
  한정하고, 필요한 주변 코드 수정은 이유를 설명해요.

## 정리 기준

- 공개 API, 사용자 동작, 상태 전이와 데이터 계약을 유지해요. 버그 수정이나 기능 변경이
  필요하면 리팩토링과 구분해 보고하고, 요청에 포함된 경우에만 수행해요.
- 기존 함수·컴포넌트·토큰과 설치된 도구를 먼저 활용해요. 불필요한 분기, 중복,
  읽기 어려운 이름과 책임 혼합을 구체적인 이점이 있는 범위에서 줄여요.
- 추측에 따른 추상화, 의존성 추가, 전역 구조 개편은 피하고 포맷만 바꾸는 변경을 섞지 않아요.
- 앱·공유 패키지의 책임 경계와 공개 export를 보존해요. 디자인 시스템과 랜딩 동작은
  해당 원본 문서를 확인하고, 구조·개발 방식이 바뀌면 `AGENTS.md`의 유지보수 규칙을 따라요.

## 확인과 결과

- 수정 후 `AGENTS.md`의 변경 유형별 검증을 수행해요. 동작 유지가 중요한 호출부와 경계 조건을
  확인하고, 실행할 수 없는 항목은 명령·원인·남은 확인 방법을 구분해요.
- 무엇을 단순화했는지, 유지한 동작, 실제 검증 결과와 남은 문제를 짧게 보고해요.
  검증 대상은 HEAD SHA와 미커밋 변경 목록으로 식별해요.
- PR 준비 흐름에서는 리팩토링 뒤의 최종 변경을 실행 검증과 자체 리뷰의 대상으로 삼아요.
  더 고칠 항목이 없다는 이유만으로 자체 리뷰나 실제 실행까지 완료했다고 쓰지 않아요.
- 이번 브랜치의 changeset이 있다면 정리 후에도 설명과 패키지 범위가 맞는지 확인해요.
  불일치는 결과에 남기고, changeset 작성은 `gdg-changeset` 단계에서 수행해요.
