# 리뷰 전 PR 제목과 본문 작성

실제 변경 내용을 근거로, 그대로 붙여 넣을 수 있는 PR 제목과 본문을 함께 작성해요. 사용자가 제목만 또는 본문만 요청하면 해당 항목만 제공해요.

## 변경 내용 확인

- 저장소 지침과 PR 템플릿을 확인해요. 사용자가 지정한 제목과 범위를 우선해요.
- 현재 브랜치, 작업 트리 상태, 비교 기준 브랜치를 확인해요. 기준은 사용자 지정, 확인 가능한 PR 대상, `develop` 순으로 판단해요. 사용할 로컬 또는 원격 추적 ref를 확인하고, fetch하지 않았다면 최신 원격이라고 단정하지 않아요.
- 기준 브랜치와의 `git diff <base>...HEAD`를 읽어요. 커밋 메시지는 맥락을 파악하는 데만 사용해요.
- 변경된 코드와 필요한 주변 코드를 확인해 실제 동작을 파악해요. 병합이나 리베이스로 반복된 커밋을 별도 변경 사항으로 세지 않아요.
- 현재 브랜치 요청에서는 커밋된 변경을 기본 범위로 삼아요. 미커밋 변경이 있으면 구분하고, 사용자 요청에 포함된 경우에만 반영해요.
- 리팩토링·검증·자체 리뷰 뒤의 최종 diff를 기준으로 작성해요. 수정 전의 요약이나 검증 결과를
  그대로 사용하지 않고, 검증한 커밋·작업 트리가 현재 작성 대상과 같은지 확인해요.
- 비교 기준을 확인할 수 없고 결과에 영향을 주면 기준을 물어봐요.

## 이 저장소에 적용할 기준

아래 경로는 저장소 루트 기준이에요.

- 루트 `AGENTS.md`와 `.github/pull_request_template.md`를 읽어요. 템플릿의
  `🎉 변경 사항`, `🚩 관련 이슈`, `📦 Changeset`, `✅ 검증 방법 및 결과`, `🙏 여기는 꼭 봐주세요!` 항목을 유지해요.
  관련 이슈를 확인할 수 없으면 `확인된 관련 이슈가 없어요.`라고 적어요.
- `apps/landing`의 사용자 동작과 `packages/wowds`의 공유 API·디자인 토큰 변경을 구분해요.
  `packages/config` 변경은 영향을 받는 앱·패키지를 확인해요.
- `docs/landing-spec.md`는 초안이에요. 현재 구현, 개선 제안, 운영·디자인 확인 항목을
  구분하고 미확정 내용을 구현 완료나 확정 정책처럼 쓰지 않아요.
- 검증 내용은 실제 실행한 명령과 결과만 적어요. `pnpm test:release`는 릴리스 도구 테스트이며
  제품 UI 테스트 통과를 뜻하지 않아요. 정의되지 않은 `pnpm test` 통과를 만들어 쓰지 않아요.
  문서만 바뀌었다면 제품 동작을 바꿨다고 쓰지 않아요.
- `docs/release-workflow.md`를 기준으로 이번 diff의 changeset 파일과 패키지·증가 종류를 확인해요.
  실제 파일이 없으면 추가했다고 쓰지 않고 구체적인 생략 사유 또는 작성 필요 항목을 남겨요.
  PR 본문 작성 중 changeset을 새로 만들거나 버전을 변경하지 않아요.
- 비교 diff가 비어 있으면 PR에 포함될 커밋 변경이 없음을 알려요. 요청에 포함되지 않은 미커밋 변경이나
  기존 분석 보고서의 문제를 이번 브랜치의 변경 사항으로 끌어오지 않아요.

## 작성 원칙

- 본문의 모든 설명 문장에 해요체를 사용해요. 변경은 '추가했어요', 동작은 '열어요', 검토 요청은 '확인해 주세요'처럼 작성해요.
- 한 문장에 한 가지 사실을 담아요. 길어지면 문장을 나누거나 항목을 분리해요.
- 짧게 쓰되 동작을 결정하는 조건, 대상, 결과는 생략하지 않아요.
- '처리했어요', '개선했어요', '연결했어요'만으로 끝내지 않아요. 무엇이 어떻게 달라졌는지 밝혀요.
- 설정 키, 반환값, 컴포넌트명은 오해를 줄일 때만 백틱으로 표기해요.
- 구현에 없는 의도나 효과를 추측하지 않아요. 실행하지 않은 검증을 완료했다고 쓰지 않아요.
- 파일별 수정 목록보다 사용자가 체감하는 변화와 리뷰에 필요한 계약 변경을 중심으로 묶어요.

## 제목 작성

- 실제 변경의 핵심을 한 줄로 요약해요. 제목은 해요체 문장 대신 간결한 구문으로 작성해요.
- 사용자가 지정한 제목이 있으면 그대로 사용해요. 지정하지 않았다면 저장소 지침과 최근 PR·병합 커밋의 제목 형식을 따라요. 예를 들어 `[FEATURE]`, `[FIX]`, `[REFACTOR]`를 사용하는 저장소에서는 해당 형식을 유지해요.
- 아직 정해지지 않은 PR 번호를 제목에 붙이지 않아요.

## 본문 구성

사용자가 형식을 지정하지 않으면 저장소의 PR 템플릿을 따라요. 템플릿도 없으면 아래 두 제목을 사용해요.

```markdown
## 🎉 변경 사항

## 🙏 여기는 꼭 봐주세요!
```

- **변경 사항:** 구현한 기능, 달라진 동작, 수정한 문제를 간결한 목록으로 작성해요.
- **Changeset:** 이번 PR의 파일·패키지·증가 종류 또는 구체적인 생략 사유를 적어요.
  버전 PR·릴리스 PR·역병합 PR은 해당 역할과 원본 버전 PR을 구분하고 기능 changeset을 요구하지 않아요.
- **검증 방법 및 결과:** 검증한 커밋과 미커밋 포함 여부, 실제 실행한 명령·결과,
  리뷰어가 따라 할 화면 재현 절차를 짧게 적어요. 실행 불가·실패·미확인 항목은 이유를 구분해요.
  직접 실행한 결과와 전달받은 결과·CI 결과를 구분하고, 근거가 없으면 미실행으로 적어요.
  다른 커밋이나 미커밋 상태의 결과는 그 대상을 밝히고 최종 변경에서 확인된 결과로 단정하지 않아요.
- **여기는 꼭 봐주세요!:** 리뷰 판단에 필요한 조건 분기, 실패 시 동작, 반환값 변경, 구체적인 확인 지점을 작성해요. 변경 사항을 그대로 반복하거나 일반적인 검토 문구로 채우지 않아요.
- 중요한 검토 지점이 없으면 '추가로 확인을 요청할 사항은 없어요.'라고 작성해요.
- 관련 이슈 등 다른 항목은 확인된 정보만 채워요. 번호나 링크를 만들지 않아요.

별도 설명 없이 제목을 먼저 `text` 코드 블록으로 제공하고, 본문을 별도의 `markdown` 코드 블록으로 제공해요. 제목과 본문을 각각 복사할 수 있게 해요. 기준 브랜치나 미커밋 변경 범위에 대한 설명이 꼭 필요하면 블록 밖에 짧게 덧붙여요.

PR 제목·본문 작성 요청만으로 파일 수정, 커밋, 원격 PR 생성·수정·게시를 수행하지 않아요. 별도로 요청받은 작업은 해당 요청 범위에 따라 진행해요.
